#[derive(Debug, Clone, PartialEq)]，为什么都需要这样声明，每个enum都默认给这些能力不就行了？

这是个很好的问题，答案核心是 Rust 的两条设计原则：**「零成本抽象」**和**「显式优于隐式」**。但更根本的原因是——**不是每个类型都"有资格"获得这些能力**。

## 1. 不是所有类型都能实现这些 trait

`derive` 宏做的是"逐字段机械展开"，但机械展开出来的代码不一定合法或有意义：

- **`Eq`**：`f64` 不能实现 `Eq`，因为 `NaN != NaN`。你的 `Expr::Number(f64)` 如果强行 derive `Eq` 就直接编译报错。看你的代码就印证了这点：`Expr` 只能 derive `PartialEq`，而纯枚举的 `UnaryOp` 才能 derive `Eq`（第 13 行 vs 第 209 行）。

- **`Clone`**：包含 `Mutex<T>`、文件句柄、`Box<dyn FnOnce()>`、`Rc` 的类型，`Clone` 要么语义模糊、要么根本不安全/不可能。

- **`Debug`**：类型里若含有无法打印的内部结构（比如持有裸指针、`dyn` 闭包），自动 Debug 会编不出来。

所以"默认给每个 enum"这个假设本身就不成立——编译器无法保证它总能生成合法实现。

## 2. 机械派生未必是你要的语义

`derive(PartialEq)` 是**逐字段比较**。但你的业务语义可能完全不同：比如一个带缓存的结构体，你只希望按 `id` 比较，忽略缓存字段。自动派生反而会给你一个"错误但能编译"的实现，埋下 bug。

## 3. 零成本：不为没用到的能力付出代价

Rust 的哲学是"你只用你付费的东西"。如果每个类型都默认生成 `Debug`/`Clone`/`PartialEq` 代码，绝大多数类型其实用不上，这会：

- 增加编译时间（每个类型都多生成代码）；
- 违背 Rust 一贯的"不为你没要求的东西承担成本"原则。

`#[derive(...)]` 这一行就是你显式向编译器下的订单："我要这三样，生成吧"。

## 4. 还有一堆 trait 根本无法 derive

`Display`、`Hash`、`Default`（部分）经常需要手写。既然"自动能力"这个机制本身就覆盖不全，Rust 选择统一的显式声明方式，而不是"有的默认、有的不默认"这种分裂规则。

---

**一句话总结**：Rust 把"要不要这个能力"的决策权交给你，是因为（a）编译器无法保证机械派生总是合法，（b）自动生成的语义未必正确，（c）默认全给会违背零成本原则。三行 derive 的成本，换来的是"类型具备什么能力一眼可见、且绝不超付"。

顺带说，也真有语言走了"默认全给"路线（Kotlin 的 `data class` 自动生成 `equals`/`hashCode`/`toString`），但它也是靠 `data` 这个关键字显式声明的，本质同样是"显式开关"，只是粒度粗一些。
